# Portfolio Rebalancing Module

A small module that models a personal investment portfolio and computes the buy/sell operations needed to bring current holdings in line with a target allocation.

## Problem

Given a portfolio of stock holdings and a target allocation, determine which stocks must be **sold** and which must be **bought** so the portfolio matches its target distribution.

## Model

The design separates three distinct concepts:

- **`Stock`** — a stock's identity plus its current price. The price is exposed through a method on `Stock`, as required by the brief. The current implementation is a placeholder; see *Price source* below.
- **`Holding`** — a position: a `Stock` plus the quantity of shares owned.
- **`AllocatedStock`** — a target: a `Stock` plus its desired weight of the portfolio (a fraction, e.g. `0.65`).

`Portfolio` holds a list of holdings and a list of target allocations, and exposes `rebalance()`.

### Why `AllocatedStock` references a `Stock`

To price a target you don't yet own (e.g. buying a certain stock from zero), the rebalance needs a `Stock` instance to ask for the price. Having the allocation reference a `Stock` keeps the price flowing through `Stock.get_current_price()` in every case.

## Rebalance logic

1. Compute `total_value` = sum of the current value of every position (price × quantity).
2. For each position whose stock **is** in the allocation: compare its current value against its target value (`allocation × total_value`). Overweight → sell the difference; underweight → buy the difference.
3. For each position whose stock is **not** in the allocation: treat the target as 0% and liquidate it fully.
4. For each allocation whose stock is **not** currently held: buy it from zero.

Operation sizes are returned as share quantities. Output shape:

```python
{"sell": [(name, shares), ...], "buy": [(name, shares), ...]}
```

## Assumptions

These are deliberate decisions, not omissions. Each is a reasonable reading of an intentionally ambiguous brief.

- **Allocations must sum to 1.0.** Enforced by validation; anything else is rejected rather than  silently normalized or accepted. (A sub-100% sum could mean "hold the rest as cash", but cash is intentionally out of scope.)
- **Prices are available for every stock in play.** If a price were missing we could not compute `total_value`, and therefore *no* target would be reliable — not just the one stock. The correct behavior is to reject the rebalance rather than operate on incomplete data, so no partial/degraded result is produced. That's why we're mocking the current price method on this exercise.
- **A held stock absent from the allocation is liquidated.** Implicit target of 0%.
- **Fractional shares are allowed.** Appropriate for a fractional-investing context; operation quantities are reported with decimals and are not rounded to whole shares.
- **Total value is fixed during a rebalance.** The method redistributes existing value only; it does not model injecting new capital.

## Price source

`Stock.get_current_price()` is a mock. In a real system the price would come from an external source (market data feed or database). For this exercise that source is stubbed; the seam is intentionally left in place rather than built out, since the brief only asks for the rebalance method.

## Testing

The tests use only the standard library (`unittest`), so nothing needs to be installed. From the project root, run:

```bash
python -m unittest test_portfolio.py -v
```

They cover the rebalance cases: an underweight stock is bought, an overweight stock is sold, an allocated stock that isn't held is bought from zero, a held stock that isn't allocated is fully liquidated, the total value stays the same, and an already balanced portfolio produces no operations. They also check that `check_total_allocation()` rejects allocations that don't sum to 1.0.
